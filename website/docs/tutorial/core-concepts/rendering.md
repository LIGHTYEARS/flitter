# 渲染管线

## 为什么要了解这个？

当你的 TUI 应用出现闪烁、卡顿、或者某块区域没有正确刷新时，理解渲染管线能帮你快速定位问题。Flitter 的渲染方式和浏览器渲染网页有很多相似之处——都是先在内存中构建一个「虚拟」表示，然后只把变化的部分同步到真实的显示上。

:::tip 一句话总结
Flitter 在内存中维护一个 Screen buffer，每帧对比前后差异，只把变化的字符通过 ANSI 转义序列写到终端。这就像 React 的 Virtual DOM diffing，只不过目标不是浏览器 DOM，而是终端屏幕。
:::

## Screen Buffer

框架维护一个 `Screen` 对象，本质是一个二维的 Cell 数组：

```ts
interface Cell {
  char: string;       // 单个字符
  style: TextStyle;   // 样式（颜色、加粗等）
}
```

:::info 类比：Screen Buffer 就是终端的「Virtual DOM」
在 Web 开发中，React 通过 Virtual DOM 在内存中表示 UI，然后对比新旧两棵虚拟树，只把差异 patch 到真实 DOM。Flitter 的 Screen buffer 做的是同样的事——它是终端屏幕的内存镜像。每一帧，RenderObject 把内容「画」到这个 buffer 上，然后框架对比新旧两帧的 buffer，只输出变化的部分。
:::

## 渲染流程

```
RenderObject.paint()
  ↓ 写入 Screen buffer（前台缓冲区）
AnsiRenderer.render()
  ↓ 对比前后两帧的 Screen buffer
  ↓ 只输出差异部分的 ANSI 转义序列
终端显示
```

### Diff 算法

逐 Cell 对比两帧的 Screen：
1. 如果 Cell 没有变化，跳过
2. 如果连续多个 Cell 变化且样式相同，合并为一次 ANSI 输出
3. 使用光标移动（`\x1b[H`）跳转到需要更新的位置

:::tip 为什么 diff 如此重要？
终端不像浏览器有 GPU 加速。每次往 `stdout` 写数据，都要经过管道传输、终端解析、重新渲染。如果每帧都全屏重绘一个 80x24 的界面（1920 个字符 + 样式序列），在 SSH 远程连接等高延迟场景下会非常卡顿。Diff 渲染意味着，如果只有一个字符变了，就只输出那一个字符的更新——这是流畅 TUI 体验的关键。
:::

## ANSI 转义序列

:::info 什么是 ANSI 转义序列？
如果你接触过终端开发，可能见过类似 `\x1b[31m` 这样的神秘字符串。这就是 ANSI 转义序列——一种终端控制协议。以 `\x1b[`（即 ESC + `[`）开头，后面跟不同的参数和字母，可以控制光标位置、文字颜色、背景色等。现代终端模拟器（iTerm2、Windows Terminal、Kitty 等）都支持这套标准。你不需要手动编写这些序列——Flitter 的渲染器会自动生成它们。
:::

框架使用标准 ANSI 转义序列控制终端：

| 功能 | 序列 | 说明 |
|------|------|------|
| 移动光标 | `\x1b[{row};{col}H` | 跳转到指定位置 |
| 设置前景色（256色） | `\x1b[38;5;{n}m` | n 为 0-255 的色号 |
| 设置背景色（256色） | `\x1b[48;5;{n}m` | n 为 0-255 的色号 |
| RGB 前景色 | `\x1b[38;2;{r};{g};{b}m` | 24-bit 真彩色 |
| 加粗 | `\x1b[1m` | 部分终端显示为高亮 |
| 重置样式 | `\x1b[0m` | 恢复默认样式 |

## 性能优化

Flitter 在渲染管线中做了多层优化来保证流畅度：

### Diff 渲染
只输出变化的区域，避免全屏重绘。这是最重要的优化——在大多数帧中，屏幕上只有一小部分发生了变化。

### 样式合并
相邻相同样式的 Cell 合并为一次输出。例如，连续 10 个红色字符只需要一次「设置红色」指令，而不是 10 次。

### 脏区域追踪
paint 阶段只处理 `markNeedsPaint()` 标记的子树。如果一个 Widget 调用了 `setState()`，只有它和它的子树会被重新绘制，其他部分完全跳过。

:::tip 实用调试技巧
遇到渲染问题时，可以尝试这些方法：
- **闪烁/残影**：通常意味着 diff 算法遗漏了某些变化。检查你的 Widget 是否正确触发了 `markNeedsPaint()`。
- **性能卡顿**：检查是否有不必要的 `setState()` 调用，导致每帧都在重建大量 Widget。`setState()` 的范围应该尽量小——只包裹真正需要更新的 State。
- **布局错位**：可能是 `performLayout()` 中的约束传递有误。确认父级的 BoxConstraints 是否正确传递给了子节点。
:::
